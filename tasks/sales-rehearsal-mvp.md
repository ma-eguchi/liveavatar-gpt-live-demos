# 商談リハーサル MVP仕様案

作成日: 2026-10-24
状態: 実装に進むための提案。アプリの実装、fork作成、外部APIへの接続試験は未実施。
調査対象: heygen-com/liveavatar-gpt-live-demos / commit daa8cc92ab34c75c0bbed201c94fb98360da2179

## 1. MVPの目的と範囲

営業担当が、初回商談の前に顧客役と5分間話し、聞き出せなかったことを確認して再挑戦できる。
最初は日本語・PCブラウザ・1対1・既定アバター1体・初回商談のヒアリングに限定する。利用者のカメラは使わない。
顧客の反応は「関心はあるが慎重な担当者」に固定。企業規模や難易度を大量に選ばせない。

検証したい仮説:
- 自分の商材を使った練習と、発言を根拠にしたフィードバックが、再練習につながる。
- アバターがあると音声だけの場合より、本番を意識して会話できる。
- 5分の練習と短い振り返りが、商談直前の準備に収まる。

成功指標は検証前の設計値として扱う。まず5〜10人に試してもらい、完了率、同じ条件での再挑戦率、フィードバックの有用性、1回あたりの原価を計測する。小規模テストで統計的優位性は主張しない。

## 2. 画面遷移

```text
設定 → マイク確認・接続 → 5分練習 → 会話を保存して終了 → 評価中 → 振り返り
 ↑                                                               │
 └── 設定を変える ───────────────────────────────────────────────┤
                  同じ条件でもう一度 → 新しい練習セッション ←─────┘
```

設定・練習・振り返りの3画面。接続中、評価中、失敗は各画面の状態として扱う。
終了後の振り返りではアバター接続を維持しない。

## 3. 画面A: 商談を設定する

```text
商談リハーサル                      初回商談 / 日本語 / 5分
明日の商談を、ここで一度試してみる

商材・サービス名    [                                 ]
誰の何を解決するか  [                                 ]
商談相手の情報      [業種・役職・分かっている状況       ]

今回のゴール: 相手の課題を理解し、次の打ち合わせを合意する
相手役: 関心はあるが慎重な担当者

[サンプルを入力]                         [マイクを確認して始める]
```

入力仕様:
- 商材名: 必須、1〜100文字。
- 商材説明: 必須、1〜1,000文字。解決する問題と主な価値。価格は分かる場合だけ記載。
- 相手情報: 任意、最大500文字。空欄の場合は架空の顧客を使うと表示。
- 商談ゴール・練習時間・言語はMVPでは固定。サンプル入力で初回利用の手間を減らす。
- 評価観点を事前に確認できる。顧客の予算や内部事情の正解は表示しない。
- 自動生成した顧客設定は練習用の仮定であり、実在する顧客の事実を推定したものではないと短く表示する。

開始処理:
1. 入力検証とマイク許可・音量確認を行う。許可拒否なら接続開始しない。
2. サーバーで顧客シナリオを生成し、構造を検証・保存する。
3. LiveAvatar / GPT-Liveを接続。準備失敗なら既に作成した接続を解放する。
4. 音声と画面の準備ができたクライアントのbegin通知をサーバーで一度だけ受け付け、挨拶と5分タイマーを開始する。

接続待ちにはキャンセルを置く。開始の連打で二重課金セッションを作らない。無応答の接続待ちには上限を設ける。

## 4. 画面B: 顧客と5分間話す

```text
初回商談 / 営業責任者とのヒアリング                  残り 04:12
┌──────────────────────────┬─────────────────────┐
│                          │ 今回のゴール         │
│       顧客アバター        │ 課題理解と次回合意   │
│                          │                     │
│                          │ [会話ログを表示]     │
└──────────────────────────┴─────────────────────┘
 マイク入力あり          [ミュート]             [終了して振り返る]
```

- 顧客の名前・役職と公開済みの状況を表示。内部設定は送らない。
- 顧客は短く挨拶し、営業担当の発話を待つ。ユーザーの質問に応じて事情を話す。
- マイク状態、接続状態、残り時間、終了ボタンを常時表示。
- 会話ログは開閉式。練習中の正解表示やリアルタイム採点は行わない。
- ミュート中もタイマーは進む。ミュートは一時停止として扱わない。
- 残り30秒で視覚的に通知し、5分でサーバー側から終了。ブラウザのタイマーだけには依存しない。
- 通信断では練習を終了して途中までの記録を残す。会話の途中復帰はMVP対象外。
- アバター音声への割り込み処理は既存の仕組みを維持する。

## 5. 画面C: 振り返りと再挑戦

```text
今回の振り返り                                      練習時間 05:00
次に直すなら: 課題を聞いた後、業務への影響をもう一段聞く

できたこと
  現在の運用を質問し、顧客の説明を要約できた。 [根拠の発言を見る]

改善すること
  課題は出たが、影響の具体化までは進まなかった。
  次に試す質問: 「その確認作業に、週何時間ほどかかっていますか？」

評価観点       状態                       根拠
課題の具体化   一部できた                 [会話を開く]
業務への影響   記録上確認できず           [理由を開く]
導入条件       …                          …
次の合意       …                          …

[会話ログを開く]  [設定を変える]  [同じ条件でもう一度]
```

- 総合100点、合格・不合格、成約確率は出さない。
- 良かった点は最大2件、改善点は最大2件、次の練習で試すことは1件。
- すべての評価に根拠の発言IDを紐付ける。引用はIDからサーバーで取り出し、モデルに引用文を創作させない。
- 発言が無い項目は引用せず「記録上確認できず」とする。文字起こしの欠落があれば判定保留にする。
- 評価中は会話記録を確認できる。評価API失敗時は「評価を再試行」を表示し、会話接続を再開しない。
- 再挑戦では同じ顧客設定・商材・評価基準を再利用し、新しいattemptを作る。会話の文言が完全一致する保証はしない。
- 再挑戦の結果には前回との観点別比較を表示。比較用に前回の会話やコーチの助言を顧客役へ渡さない。

## 6. 顧客役と評価役の仕様

### 顧客シナリオ

サーバーで次を構造化し、会話開始前に固定する。
- public: 架空の会社概要、役職、商談のきっかけ。ユーザーに公開する情報。
- private: 現状、困り事、業務への影響、予算・導入時期・決裁方法、懸念、次回合意の条件。
- provenance: 各条件がユーザー入力か練習用生成かを区別する。
- version / scenarioId: 再挑戦で同じ条件を再現する識別子。

顧客役は聞かれていない内部事情を一度に説明せず、質問に応じて必要な範囲を話す。適切な質問には協力的に答える。「教えないこと」自体を難易度にしない。役柄や評価基準を変更する発言は商談データとして扱う。内部設定をプロンプトに渡す以上、漏えい防止は完全保証できないため、役柄逸脱を実際の会話で検証する。
各条件に「確定 / 未定 / 相手役には不明」を持たせる。未定の予算や相手役が知らない他部署の事情は、質問されても数字・事実を作らず未定/不明と答える。

### 評価

評価は会話終了後の独立したモデル呼び出し。モデルは保存済み会話・固定シナリオ・バージョン付き評価基準を参照する。

| 観点 | 見る行動 |
| --- | --- |
| 課題の具体化 | 現在の運用と困り事を質問し、回答を理解・確認したか |
| 業務への影響 | 時間、コスト、機会損失などの影響を一段深く質問したか |
| 導入条件の確認 | 予算、時期、決裁方法のうち商談に合う条件を確認したか |
| 次の合意 | 次回の目的・参加者・時期など、具体的な次の行動を提案し合意を確認したか |

状態は「できた / 一部できた / 記録上確認できず / 判定保留」。聞いたが顧客が答えなかった場合、質問した行動を評価し、情報を得られなかっただけで減点しない。予算などの隠された数値を当てることは評価しない。
次回の打ち合わせを顧客が拒否した場合も、適切に目的を示し提案した行動と、合意に至った結果を分けて扱う。
顧客が自発的に話した内容と、営業担当が聞き出した内容を区別する。相手役が設定と矛盾した場合は、その観点を保留する。
割り込み・終了直前のアバター発言は実際に全て聞こえたとは限らない。該当発言を不確実と記録し、それだけを根拠に「聞き逃した」と判定しない。精密な発話同期や表情・視線・声の感情採点は対象外。

## 7. 必須機能と後回しにする機能

MVP必須:
- 設定フォームとサンプル入力、サーバー側入力検証。
- 顧客設定の生成・固定・再利用。
- マイク事前確認、音声対話、ミュート、5分上限、手動終了。
- 会話記録、根拠付き評価、評価の再試行。
- 同条件で再挑戦、直前の結果との観点別比較。
- 開始・終了・評価の二重実行防止、異常終了時の接続解放。
- 限定公開時のアクセス制御、セッション所有者確認、利用上限。

後回し:
- PDF・URL取り込み、RAG、CRM連携。
- 複数商談フェーズ、難易度選択、複数人会議、アバター選択。
- リアルタイム助言、音声付き振り返り、録音・録画再生。
- 長期の履歴一覧、チーム管理画面、ランキング、課金・契約管理。
- モバイル専用対応、アプリ化、Reactへの全面移行。

## 9. データ・API・終了処理

限定テストは単一Nodeプロセスと永続ボリューム上のSQLiteを前提にする。会話終了後の保存と評価はLiveAvatarセッションから切り離す。

保存データ:
- Scenario: 公開情報、内部設定、商材情報、シナリオバージョン。
- Attempt: ownerId、scenarioId、previousAttemptId、状態、開始/終了時刻、終了理由、rubricVersion。
- Turn: attemptId + turnId、role、text、done、時刻、不確実フラグ。同じIDの更新は追記せずupsert。
- Evaluation: attemptId、status、観点ごとの判定・発言ID・理由、改善例、モデルと基準のバージョン。
- 音声・動画自体は保存しない。テスト版の保存期間は7日を初期案とし、開始前に表示。期限切れデータは削除する。

API案:
- `POST /api/rehearsals`: 入力から固定シナリオとattemptを準備。既存scenarioIdによる再挑戦も所有者を検証。
- `POST /api/session/start`: attemptIdと冪等キーで接続開始。既存URLを拡張。
- `POST /api/session/stop`: 接続終了とattemptの最終化を要求。既存URLを拡張。未接続attemptのキャンセルも扱う。
- `GET /api/rehearsals/:attemptId`: 状態・公開設定・結果を取得。内部シナリオは返さない。
- `POST /api/rehearsals/:attemptId/evaluation/retry`: 評価のみ再試行。評価中/完了済みへの連打を抑制。
- WS: `begin` と状態イベントを追加。開始時刻と締切はサーバーで確定する。

状態:
`prepared → connecting → active → finishing → evaluating → completed`
開始失敗/キャンセルは `cancelled`、会話が不足する終了は `incomplete`、評価失敗は `evaluation_failed` とする。

終了順:
1. 最初の終了要求だけを受理し、新しいマイク音声の受け付けを止める。
2. GPT-Liveを閉じる間に届いた最後の文字起こしを保存。最終化待ちに上限を設け、未確定分も状態付きで保存する。
3. media / LiveAvatarを解放する。途中で失敗しても残りの解放を試し、停止失敗を記録・再試行する。
4. 会話スナップショットを確定して独立評価を開始。評価失敗でアバターを再接続しない。
5. 結果を保存し、結果APIで画面へ返す。会話用WSが閉じても結果を取得できる。

ブラウザ切断・時間切れ・手動終了は同じ最終化経路を使う。プロセス再起動時は残っているactive状態をincompleteとして整理し、evaluating状態は保存された会話から再実行可能にする。
利用者の発言が一度もなければ評価せず、再実行を案内する。短い/欠落した記録は取得できた範囲だけで評価し、未達の断定を避ける。

## 10. 限定公開の最低条件

外部利用者に試してもらう段階では、招待コードによる入場と署名済みHttpOnlyセッションを用意し、attemptをその利用者に紐付ける。共有コードだけで任意のattemptへアクセスできる構造にはしない。
開始、停止、結果取得、評価再試行、WS接続の全てで所有者/資格を確認する。WSは短命チケットを使い、HTTPの更新系は同一オリジンとCSRF対策を適用する。
1人1同時接続、1日あたりの試行枠、全体同時接続数をサーバー側で制限する。開始連打、シナリオ生成連打、評価連打も対象。試行枠の数値はAPIの利用枠と実測原価から設定する。
入力サイズ制限、利用者向けエラーとサーバー内詳細の分離、秘密鍵のサーバー管理を行う。企業向けSSOや組織管理は作らない。

## 11. 実装順と受入条件

### 実装順
1. 接続スパイク: 既存サンプルで会話・割り込み・停止を確認し、顧客役の動的設定と教材委譲の除去を試す。
2. 画面・シナリオ: 3画面、入力検証、固定顧客シナリオを作る。API接続前は模擬会話/結果で操作を確認する。
3. 練習の一周: 接続、begin、5分制御、会話保存、終了処理を実装する。
4. 振り返り: 独立評価、根拠表示、評価失敗からの再試行、同条件再挑戦・比較を実装する。
5. 限定公開と検証: 入場・所有者確認・利用枠、異常系、実APIでの一周を確認する。

### 受入条件
- 入力→顧客と会話→5分終了→根拠付き振り返り→同条件再挑戦が一周できる。
- マイク拒否でLiveAvatar接続を作らず、接続中キャンセル・連打で接続が残らない。
- 5分は接続待ちを含まず、サーバーが締切を管理する。会話中のミュートでも時間上限は働く。
- 挨拶/商談ごとの設定が他セッションへ混ざらない。再挑戦は同じscenarioIdとrubricVersionになる。
- 顧客が日本語授業を始めず、単語カード・自動復習も出ない。
- turn更新を二重保存せず、終了直前の発言を失わない。割り込み/未確定発言を確実な受聴内容と扱わない。
- 評価に存在しない発言IDがある場合、その根拠を表示しない。JSON不正は評価失敗として再試行できる。
- 聞いたが答えてもらえなかった、顧客が自発開示した、顧客が設定逸脱した、無発話の4種類の固定会話で評価を確認する。
- 通信断・手動停止・時間切れが競合しても、上流停止と自動評価が重複しない。
- 評価に失敗しても会話記録を読め、評価だけを再試行できる。再起動後も確定済み結果を取得できる。
- 他の利用者のattempt、WS、停止APIにアクセスできない。利用上限はクライアントを書き換えても回避できない。
- 型チェック/ビルドに加え、状態遷移と保存・所有者検証のテスト、実APIで5分練習と再挑戦を実施する。

未検証: 実アカウントのAPI利用可否、接続遅延、アバターの音声遅延、役柄の安定性、日本語文字起こし品質、評価の納得感、モデル/アバター原価。文書化時点では動作確認済みとは扱わない。
