# ポートフォリオ：Talk with Masahiro

AIアバターと声で会話して英語を学ぶ Web アプリ。要件定義から公開まで個人で開発しました。

- 公開URL：`https://<your-app>.vercel.app`
- ソース：https://github.com/ma-eguchi/liveavatar-gpt-live-demos
- 期間・体制：個人開発（要件定義、設計、実装、テスト、デプロイ）

## 1. 要件定義

### 解きたい課題
英語初心者がつまずくのは「知っている単語が口から出ない」ことです。
テキストのアプリでは話す練習ができず、人間の講師は予約と費用のハードルが高くなります。
そこで、**相手の顔を見ながら声でやり取りでき、いつでも始められる練習相手**を作りました。

### 機能要件
| # | 要件 | 実装 |
| --- | --- | --- |
| F1 | ボタン操作なしで、声だけで会話できる | GPT-Live（全二重の音声モデル）に、話し終わりと割り込みの判断を任せる |
| F2 | 相手の顔が見える | HeyGen LiveAvatar の映像を LiveKit で配信 |
| F3 | 教わったフレーズを目で確認できる | 発音（カタカナ）と意味のカードを映像の上に重ねて表示 |
| F4 | 学んだことが残る | レッスン終了時に単語帳と履歴へ自動保存 |
| F5 | 復習できる | 単語帳、「覚えた」チェック、フラッシュカード、読み上げ |
| F6 | 本人だけが自分の記録を見られる | Supabase Auth と RLS |

### 非機能要件
| # | 要件 | 方針 |
| --- | --- | --- |
| N1 | **費用に上限がある**（1回ごとに外部 API の料金が発生） | ログイン必須、1日3回（DB で判定）、1回5分（サーバーで強制終了） |
| N2 | API キーを漏らさない | ブラウザには視聴トークンと使い捨てチケットだけを渡す |
| N3 | AI の出力を信用しない | サーバーで検証し、`textContent` でのみ表示。単語リストもサーバーの記録から作る |
| N4 | スマホでも使える | レスポンシブ対応（幅 390px で横スクロールなし） |
| N5 | 1人で運用できる | マネージドサービスだけで構成し、デプロイ手順を文書化 |

## 2. 設計

### 全体構成と、なぜこう分けたか
```
Next.js (Vercel)  ──共有シークレット──►  オーケストレーター (Node, Docker)
   │ Supabase Auth / RLS                    │ GPT-Live ⇄ LiveAvatar の音声中継
   ▼                                        ▼
Supabase Postgres  ◄──── service role ─── 終了時に単語と履歴を保存
```
- **Vercel だけでは完結しません**。音声中継には数分間つなぎっぱなしの WebSocket が必要で、サーバーレス関数では保持できません。
  そこで、画面と認証（Next.js）と、音声中継（常駐プロセス）をサービスとして分けました。
- **アバターを起動できる入口を Next.js の1か所に絞りました**。オーケストレーターは共有シークレットを持つ呼び出しにしか応答しないため、
  ログインと回数チェックを通らずにアバターを起動する経路がありません。
- **ブラウザからの WebSocket 接続は、セッションごとの使い捨てチケットと Origin で確認します**。
  Vercel は WebSocket を中継できないため、ブラウザはオーケストレーターに直接つなぎます。この接続を守るための仕組みです。

### データモデル（`supabase/migrations/0001_init.sql`）
| テーブル | 役割 |
| --- | --- |
| `profiles` | ユーザーごとの1日の上限（`daily_limit`、初期値3）。サインアップ時にトリガーで作成 |
| `practice_sessions` | レッスン1回分。`starting → ended / failed` |
| `words` | 単語帳。`(user_id, lower(term))` を一意にして重複をまとめ、出てきた回数を数える |
| `session_words` | どのレッスンでどの単語が出たか（履歴の表示用） |

**回数制限を SQL 関数で行う理由**：アプリ側で「数えてから登録する」と、タブを2つ開いて同時に押されたときに上限を超えます。
`start_practice_session()` はユーザー単位のアドバイザリーロックの中で「数える＋登録する」を行うので、競合しても上限を超えません。
アバターの起動に失敗した場合は `fail_practice_session()` で回数を戻します。

**書き込める人を役割ごとに分けています**：ブラウザが更新できるのは `words.mastered` の1列だけです（列単位で GRANT）。
レッスンの終了記録は service role だけが呼べる `record_session_end()` 経由でしか書けず、同じレッスンを2回記録しても結果は変わりません。

## 3. 実装したもの（担当範囲）

音声中継の土台は HeyGen 社の MIT ライセンスのリファレンス実装を使っています。
次の表は、元のコードと自分で作った部分の区別です。

| 領域 | 元のリファレンス実装 | 自分で実装・変更した部分 |
| --- | --- | --- |
| 画面 | Vite の1ページ（認証なし） | **Next.js App Router で作り直し**：LP、ログイン、練習、履歴、単語帳、フラッシュカード、404 |
| 認証 | なし | **Supabase メールリンク認証**、`proxy.ts` でのセッション更新とページの保護、ログイン後の安全なリダイレクト |
| DB | なし | **スキーマ、RLS、列単位の権限、回数制限・終了記録の SQL 関数** |
| API | オープンなセッション開始 | **`/api/session/start`**（認証 → 回数 → 起動 → 失敗時に回数を戻す）、`/api/session/stop`（本人確認つき） |
| オーケストレーター | ローカル用（認証なし） | **本番モード**：共有シークレット（定数時間比較）、WebSocket の使い捨てチケット、Origin 制限、時間上限、終了時の DB 保存（リトライつき） |
| 不具合修正 | — | サーバー側で終了したとき（時間切れ、接続切れ、無操作）にブラウザへ通知されず、画面が「接続中」のまま止まる問題 |
| ブラウザのセッション制御 | DOM を直接操作する main.ts | React から使えるクラスに移植。単語の収集、残り時間、日本語のエラー表示 |
| ペルソナ | 汎用 | 日本人初心者向けの英会話コーチ「Masahiro」のプロンプトとレッスン設計 |
| 運用 | — | Dockerfile、Render Blueprint、デプロイ手順書、環境変数の検証 |

## 4. テスト・検証

| 対象 | 方法 | 結果 |
| --- | --- | --- |
| SQL（回数制限、RLS、権限、冪等性） | ローカルの Postgres 16 に Supabase の `auth` スキーマを模したものを作り、2ユーザーで検証 | 4回目の開始を拒否、失敗した回は回数に戻る、他人のデータは0件、`mastered` 以外は更新不可、二重記録しても変化なし、大文字・小文字違いの単語は1つにまとまる |
| オーケストレーターの本番モード | LiveAvatar と Supabase の偽サーバーを立てて結合テスト | シークレットなし・誤りは 401、不正な入力は 400、チケットなし・誤りは 401、許可していない Origin は 403、2つ目のブラウザは拒否、終了時に保存の RPC が呼ばれる、時間切れでブラウザに通知され接続が閉じる |
| 画面全体 | Playwright と偽の Supabase で、ログイン済みの状態を再現 | 未ログイン時のリダイレクト、練習開始から回数が増えて失敗時に後片付けされるまでの流れ、単語カードの表示、履歴・単語帳・絞り込み・フラッシュカード・「覚えた」の保存を確認。スマホ幅で横スクロールなし |
| 型・ビルド | `pnpm typecheck` / `next build` | 通過 |

## 5. 工夫したこと・学んだこと

- **費用を設計で抑える**：1回ごとに料金がかかる API を公開するため、「誰が」（認証）、「何回」（DB での回数判定）、「何分」（サーバーでの強制終了）の3段階で上限を設けました。
- **AI に任せない部分を決める**：教えた単語のリストを AI に答えさせると、言っていない単語が混ざります。
  サーバーが実際に表示したカードを記録し、そこから振り返りパネルと単語帳を作ります。
- **使っている側に失敗を見せる**：時間切れや接続切れをブラウザに伝えないと、利用者は止まった画面の前で待ち続けます。
  元の実装にあったこの問題を見つけて直しました。
